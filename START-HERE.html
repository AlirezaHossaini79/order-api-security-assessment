‏تسک عملی سید علیرضا حسینی — Security

‏این بسته صرفاً محیط آزمایشی با اطلاعات ساختگی است. نامزد: سید علیرضا حسینی؛ نقش: Security؛ شناسه: 04-hosseini-security؛ نسخه: 1.0.

‏زمان پیشنهادی اجرا ۴ تا ۶ ساعت؛ مهلت تحویل ۳ روز کاری پس از دریافت. پس از سقف زمانی، همان نتیجه موجود و موارد ناتمام را تحویل دهید. افزایش امکانات خارج از خواسته‌ها امتیاز ندارد. منابع: Docker Compose v2 و Python 3.10+، اینترنت برای دریافت image و dependency؛ حدود ۴ هسته، ۶ گیگابایت RAM و ۸ گیگابایت فضای آزاد.

‏استفاده از ابزارهای هوش مصنوعی مجاز است. مسئولیت صحت، امنیت و توضیح تمام تغییرات با شماست. ابزارهای استفاده‌شده، کارهای واگذارشده و یک نمونه پیشنهاد نادرست ابزار و نحوه بررسی آن را ذکر کنید؛ اگر موردی نبود صادقانه بنویسید. امتیاز مستقلی بابت استفاده یا عدم استفاده از AI وجود ندارد.

‏اجرا از پوشه lab: دستور `docker compose -p hr-hosseini up -d --build` و سپس `python tools/smoke.py`. سرویس روی http://127.0.0.1:18080 است. هر بار فقط یک بسته را اجرا کنید. توقف بدون حذف داده: `docker compose -p hr-hosseini down`. پاک‌سازی اختیاری و مخرب فقط داده همین تمرین: `docker compose -p hr-hosseini down -v`.

‏محیط اولیه عمداً کامل و مقاوم نیست. برای کنترل خرابی از `python tools/control.py --delay-ms 1500` و برای بازنشانی از `python tools/control.py` استفاده کنید. خطای تجاری HTTP 200: گزینه `--business-fail`. نام release در این ابزار صرفاً برچسب است و جای استقرار نسخه واقعی را نمی‌گیرد. قطع وابستگی: `docker compose -p hr-hosseini stop db`؛ بازیابی: همان دستور با `start db`. این کنترل‌ها داخل هر نمونه API مستقل و در حافظه‌اند.

‏بار نمونه: `python tools/traffic.py --requests 100 --workers 5`. خروجی خام را ذخیره کنید. هر درخواست به طور پیش‌فرض کلید مستقل دارد؛ `--key retry-demo` یک کلید مشترک می‌فرستد. توکن‌های ساختگی: lab-alice، lab-bob و lab-ops. نمونه سفارش‌های اولیه ۱ متعلق به alice و ۲ متعلق به bob است؛ برای تست مالکیت، شناسه را از سفارش جدید بگیرید و به ثابت بودن seed اتکا نکنید. API: POST /orders با JSON دارای item؛ GET /orders/ID؛ /live؛ /ready؛ /metrics.

‏تحویل: کل سورس قابل اجرا به همراه تغییرات، فایل dependency با نسخه، README اجرا از محیط پاک، پوشه evidence با خروجی خام زمان‌دار و فرمان تولید آن، و SUBMISSION.md تکمیل‌شده. اسکرین‌شات به‌تنهایی مدرک کافی نیست. فایل‌های حجیم image، volume، کلید واقعی و اطلاعات شخصی را ارسال نکنید. برای بررسی، بسته شما از محیط پاک اجرا و سناریوهای اعلام‌شده با داده و زمان‌بندی متفاوت تکرار می‌شوند.

‏جلسه دفاع ۳۰ دقیقه است: ۱۰ دقیقه اجرای مجدد، ۱۰ دقیقه توضیح تصمیم‌ها و ۱۰ دقیقه تغییر کوچک در سناریو. همه معیارهای فنی قابل امتیاز در این برگه آمده‌اند؛ آزمون پنهان صرفاً برای راستی‌آزمایی همین معیارهاست. نتیجه آزمون یکی از ورودی‌های تصمیم استخدام است.

‏کشف و اولویت‌بندی — ۲۵ امتیاز

‏برای همین محیط threat model مختصر شامل دارایی‌ها، مرز اعتماد و مهاجم بنویسید. یافته‌ها را با محل دقیق، پیش‌شرط، اثر و شدت اولویت‌بندی کنید. اسکنر می‌تواند کمک کند؛ گزارش خام اسکنر جای تحلیل را نمی‌گیرد. نشانه‌های اولیه شامل کنترل مالکیت و دسترسی به تنظیمات است؛ سایر یافته‌ها باید شاهد داشته باشند.

‏اثبات ایمن — ۲۵ امتیاز

‏در همین lab، دسترسی alice به سفارش bob و افشای تنظیمات حساس را به طور غیرمخرب بازتولید کنید. درخواست و پاسخ پالایش‌شده و تست قابل اجرا تحویل دهید. توکن‌ها و رمزهای این بسته ساختگی‌اند؛ هیچ سیستم، دامنه یا IP دیگری در scope نیست. DoS، حمله به میزبان و دریافت داده واقعی خارج از محدوده است.

‏رفع و تست پس‌رفت — ۳۵ امتیاز

‏هر دو مورد را رفع کنید و کنترل /lab/control را برای نقش ops محدود کنید. alice فقط سفارش خودش را ببیند؛ bob فقط سفارش خودش؛ نقش ops در این تمرین مجاز به مشاهده سفارش‌هاست. کاربر بدون توکن یا توکن نامعتبر نباید دسترسی بگیرد. تست مثبت و منفی، عدم افشای DSN/رمز و محدودسازی دسترسی DB/اجرای container را ارائه کنید؛ حذف کل قابلیت سفارش راهکار قابل قبول نیست.

‏تحویل و اثر — ۱۵ امتیاز

‏تفاوت remediation انجام‌شده با ریسک پذیرفته‌شده را بنویسید. secret ساختگی را از سورس تنظیمات به سازوکار مناسب منتقل و روش تزریق را مستند کنید. محدودیت توکن‌های ثابت و اقدام لازم برای production را روشن کنید؛ سرویس باید از محیط پاک اجرا شود.

‏شرط قبولی

‏حداقل نمره کل ۸۰ از ۱۰۰، حداقل ۶۰٪ امتیاز هر بخش و عبور از شرط‌های الزامی. نمره بالا در یک بخش، شکست الزامی بخش دیگر را جبران نمی‌کند.

‏باقی ماندن دسترسی بین کاربران یا افشای DSN، و نیز از کار انداختن دسترسی مجاز، مانع قبولی است.

‏ناتوانی در اجرای مجدد بخش اصلی یا توضیح و تغییر راهکار در دفاع زنده، مانع تأیید نهایی است. قطعی اینترنت یا کمبود منابع محیط داوطلب جداگانه بررسی می‌شود.
