# گزارش امنیت — 04-hosseini-security

## محدوده و مدل تهدید

محدوده فقط همین آزمایشگاه و داده‌های ساختگی آن است. دارایی‌ها: سفارش و مالکیت آن، رمزهای DB، کنترل رفتار سرویس، و اطلاعات تشخیصی. مهاجم می‌تواند یک کاربر عادی دارای توکن یا یک مراجعه‌کننده بدون توکن باشد. در محیط عمومیِ انتخاب‌شده توسط کاربر، اینترنت نیز به پورت API دسترسی دارد.

مرزهای اعتماد: کلاینت → API؛ توکن → هویت و نقش؛ API → DB؛ میزبان → کانتینر؛ فایل رمز میزبان → mount فقط‌خواندنی. ورودی کلاینت نباید مالکیت یا نقش را تعیین کند. داشتن توکن معتبر به‌تنهایی مجوز خواندن همه سفارش‌ها نیست.

## یافته‌های اولویت‌بندی‌شده

شماره خطوط زیر مربوط به سورس اولیه داخل بسته دریافت‌شده است، نه فایل اصلاح‌شده.

| شناسه | شدت در این lab | محل اولیه | پیش‌شرط و اثر | وضعیت |
|---|---|---|---|---|
| S01 | بالا | `lab/app/app.py:78`، خواندن سفارش | کاربر دارای توکن با ID سفارش دیگران، owner/item/request_key او را می‌خواند | رفع شد: شرط مالکیت در خود query؛ استثنا فقط ops |
| S02 | بالا | `lab/app/app.py:56`، `/debug/config` | بدون توکن، DSN حاوی رمز DB دریافت می‌شود؛ اطلاعات امکان دسترسی به DB در صورت وجود مسیر شبکه را فراهم می‌کنند | رفع شد: کنترل ops و پاسخ allowlist فاقد DSN/رمز حتی برای ops |
| S03 | بالا | `lab/app/app.py:50`، `/lab/control` | بدون توکن، مهاجم می‌تواند رفتار سفارش‌ها و تأخیر/خطای تجاری را تغییر دهد | رفع شد: احراز هویت، مجوز ops و اعتبارسنجی ورودی |
| S04 | متوسط | `lab/app/app.py:41-43` و `/metrics` | URL شامل query به شمارنده‌ها و لاگ می‌رود؛ metrics عمومی می‌تواند آن را افشا کند؛ مسیرهای متفاوت حافظه را افزایش می‌دهند | رفع شد: دسترسی ops، routeهای ثابت در metrics و لاگ، جمع تجمعی زمان بدون لیست نامحدود |
| S05 | بالا، وابسته به دسترسی به سورس/کانتینر | `lab/compose.yaml:6,18`؛ `lab/app/app.py:6` | رمز ثابت در سورس و DSN محیط API؛ اپ با همان نقش bootstrap دیتابیس کار می‌کند | رفع شد: رمزهای تصادفی فایل‌محور، چرخش رمز اولیه، نقش مستقل بدون قابلیت مدیریتی و فقط SELECT/INSERT |
| S06 | متوسط، عامل افزایش اثر نفوذ | `lab/app/Dockerfile` و تنظیمات api در Compose | Dockerfile فاقد USER است؛ پس کد API به‌طور پیش‌فرض root اجرا می‌شود و فایل‌سیستم نوشتنی است | رفع شد: UID/GID=10001، rootfs فقط‌خواندنی، drop ALL capabilities، no-new-privileges و محدودیت PID |

شدت‌ها ارزیابی کیفی همین محیط هستند و نمره CVSS رسمی نیستند. S01 تا S04 با HTTP بازتولید شدند؛ S05 و S06 با بررسی سورس اولیه و بررسی تنظیمات واقعی پس از رفع ارزیابی شدند. نبود publish برای DB از قبل وجود داشت؛ به‌عنوان باگ جدید ادعا نمی‌شود. در نسخه جدید شبکه داخلی DB هم اضافه شده است.

## اثبات غیرمخرب و نتیجه

`evidence/before.json` شامل ۶ بررسی موفق برای نشان دادن وضعیت اولیه است: ساخت سفارش تازه توسط آلیس و باب، خواندن سفارش باب توسط آلیس، افشای config بدون توکن، پذیرش control خالی بدون توکن و ورود marker ساختگی query به metrics عمومی. درخواست control خالی هیچ وضعیت خرابی را فعال نمی‌کند. هیچ DoS، داده واقعی یا هدف دیگری استفاده نشده است.

`evidence/after.json` شامل ۳۵ بررسی نسخه اصلاح‌شده است: دسترسی مالک/ops، منع هر دو جهت دسترسی بین کاربران، توکن نامعتبر/غایب، مجوز کنترل و config و metrics، نبود DSN/رمز در config مجاز، ورودی نامعتبر، روش HTTP و سلامت سرویس. منع دسترسی مالکیت با 404، برای پرهیز از افشای وجود سفارش، پیاده شده است.

`evidence/runtime.json` شامل ۱۰ بررسی واقعی کانتینر و DB است: کاربر غیر root، rootfs فقط‌خواندنی، حذف قابلیت‌ها، منع افزایش امتیاز، عدم publish دیتابیس، نبود DSN در محیط API، mount فقط رمز اپ، شبکه داخلی DB، فقدان نقش مدیریتی و مجوزهای محدود داده.

`evidence/clean-run.log` و `clean-security.json` و `clean-runtime.json` اجرای همان بررسی‌ها با پروژه تصادفی، volume تازه و رمز تازه را ثبت می‌کنند. فرمان‌ها و زمان‌ها داخل فایل‌ها هستند. تست بار نمونه ۱۰۰ درخواست با ۵ worker در همان لاگ ثبت شده است. این تست بار یک benchmark یا ادعای مقاومت در برابر DoS نیست.

## تصمیم‌های اصلاح و ریسک باقی‌مانده

- **رفع انجام‌شده:** کنترل مالکیت و نقش، حذف اطلاعات اتصال از پاسخ، جداکردن نقش DB، خروج رمز از سورس جدید و از محیط API، چرخش رمز اولیه در مهاجرت، محدودسازی کانتینر و شبکه و جلوگیری از ثبت query در diagnostics.
- **ریسک پذیرفته‌شده برای تمرین:** توکن‌های ثابت lab قابلیت انقضا، لغو یا اتصال به هویت واقعی ندارند و هرکس توکن باب را بداند می‌تواند باب شود. در production باید با احراز هویت واقعی، توکن کوتاه‌عمر با اعتبارسنجی معتبر و سازوکار rotation/revocation جایگزین شوند.
- **دسترسی عمومی فعلی:** به درخواست کاربر، پورت 18080 روی آی‌پی عمومی است. این محیط TLS و مدیریت هویت production ندارد؛ تنظیم پیش‌فرض بسته تحویل loopback است. برای production نیاز به TLS و محدودسازی دسترسی مدیریتی و مسیرهای مانیتورینگ است.
- **مرز DB:** نقش اپ مجوز مدیریت یا تغییر schema ندارد، اما برای اجرای قابلیت سفارش SELECT/INSERT جدول را دارد؛ جداسازی ردیفی در API اعمال می‌شود. تصرف کامل پردازش API همچنان می‌تواند همه ردیف‌های قابل SELECT را در معرض خطر بگذارد. RLS دفاع تکمیلی است و در محدوده این تمرین اضافه نشده است.
- **محدودیت سرویس اولیه:** از HTTP server کتابخانه استاندارد استفاده می‌شود؛ rate limiting، timeoutهای production و توزیع state اضافه نشده‌اند. کنترل خرابی داخل حافظه هر نمونه باقی می‌ماند. کلید Idempotency ذخیره می‌شود ولی تضمین جلوگیری از سفارش تکراری ندارد؛ این قابلیت معیار امنیتی درخواست‌شده نبود.
- **نگه‌داری رمز:** Compose secret محلی فایل‌محور است و رمزنگاری در حالت ذخیره‌سازی ایجاد نمی‌کند. مدیر میزبان همچنان به رمزها دسترسی دارد. برای production، secret manager و چرخه rotation لازم است. نسخه اولیه/آرشیوهای قدیمی همچنان حاوی رمز ساختگیِ قبلی‌اند؛ با مهاجرت، آن رمز برای DB اصلی عوض می‌شود.

هیچ اسکنر آسیب‌پذیری یا اسکن وابستگی اجرا نشده است؛ این گزارش ادعای نبود تمام آسیب‌پذیری‌ها یا بررسی CVEها ندارد.

## راهنمای دفاع ۳۰ دقیقه‌ای

۱. ده دقیقه اول: اجرا از README، ساخت سفارش‌های تازه و تست security و runtime؛ از ID ثابت استفاده نشود.

۲. ده دقیقه دوم: توضیح تفاوت authentication و authorization، شرط مالکیت در query، علت 404، پاسخ allowlist تنظیمات، نقش محدود DB و تفاوت secret فایل‌محور با secret manager.

۳. ده دقیقه آخر: تغییر کوچک مانند افزودن کاربر آزمایشی و بررسی دسترسی او یا تغییر پورت با LAB_PORT؛ سپس اجرای مجدد تست‌های مرتبط. دفاع زنده باید توسط خود نامزد انجام شود و هنوز انجام نشده است.
